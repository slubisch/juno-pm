## Four Levers

**Stop Conditions** (Loop):

I recommend these as **initial V1 stop conditions**, then validate them against representative customer files:

#### 🔁 03 Loop · Stop conditions

- **Max steps: 12.** A step is one source read or extraction, synthesis, verification, or repair action. User review does not count. At the limit, Juno stops and returns its best result labeled **“step limit reached”** and **incomplete**.
- **Early abort: 2 consecutive processing failures.** A failure is a tool error or an inability to read, parse, or verify a selected source. Conflicting or missing information in readable sources is **not** a processing failure; Juno reports it for review. If no selected source can be used, Juno stops immediately. It identifies failed sources and does not save changes.
- **Wall-clock timeout: 90 seconds** from **Analyze** to a reviewable synthesis. On timeout, Juno stops and returns any partial result labeled **“timed out”** and **incomplete**, with processed and failed sources listed. It does not save changes.

These put limits on loop length and runtime. They don’t guarantee a dollar ceiling; keep the per-analysis financial cap as a separate launch decision, as previously agreed.

**Structured Tool Outputs** (Tools):

#### 🛠️ Lever 2 · Tools — Structured outputs

Every Juno tool returns a structured object. Juno uses `status`, `error.code`, and numeric counts to decide what happens next; any human-readable message is display-only.

**Common envelope**

```json
{
  "status": "ok | partial | error",
  "data": {},
  "counts": {},
  "warnings": [],
  "error": null
}
```

For errors, `error` contains a stable `code` and a `retryable` boolean. A partial result includes both usable results and per-item failure codes. Source conflicts are returned as warnings or review items, not tool failures.

The listed error codes are proposed contract values for the PRD; implementation should use the same codes consistently across tools.

**Confidence Thresholds** (Verification):

#### 🔎 Lever 3 · Verification — Confidence thresholds

For Juno, confidence determines whether a finding can appear in the draft. **It never authorizes Juno to save or apply changes:** all writes still require user confirmation.

Assess confidence **per claim or proposed field change**, based on how direct, clear, and consistent the source evidence is. Show the supporting source and relevant location.

- **High — 80% or higher:** Include the finding in the draft with its source citation.
- **Review — 50% to 79%:** Include it as tentative and flag it for the user to check. Don’t use it to change a saved field or drive a report metric without approval.
- **Low — below 50%:** Don’t present it as a factual finding or propose it as an update. Mark it as unknown or unresolved if it matters to the profile.

A missing source or unresolved conflict always requires review, regardless of the estimated confidence. For ARR, renewal date, and risk, Juno may propose the XLS value as authoritative, but it must still show conflicting evidence and wait for user approval. Confidence bands are rough evidence judgments, not calibrated model probabilities.

**North Star** (Context):

**North Star:** Juno turns authorized, customer-scoped sources into a clear, evidence-linked profile and proposed workspace updates; it must never mix customers’ data or apply changes without user approval.

## Rules of Engagement

**Agency Permission:**

**Agency permission:** Juno may read selected customer sources, assess evidence, and draft profile summaries and proposed customer, Backlog, or Report changes on its own. It must wait for explicit user confirmation before saving data, creating a customer record, or applying changes; sending external messages is blocked.

**Access Control:**

**Access control:** In V1, Juno can access the selected customer record and files or text the user provides for that customer. It cannot directly access Webex, Jira, Airtable, or OneNote, or read other customers’ data. Future integrations must be authorized, read-only, and customer-scoped.

**Fallback Protocols:**

**Fallback protocol:** When the 12-step limit, two consecutive processing failures, or 90-second timeout is reached—or when no usable sources remain—Juno stops and returns any usable work as **incomplete**. It reports a machine-readable `stop_reason`, lists processed and failed sources, and tells the user what needs attention. It does not save or apply changes; the user can correct the inputs and start another run.

**Checkpoints:**

**Checkpoints:** Juno pauses for user review before any persistent write. After analysis, it shows the synthesis and each proposed customer, Backlog, or Report change with its evidence, source location, and confidence. The user can approve or reject changes and choose whether imported information updates a field or is stored as supporting evidence. Until approval, the synthesis remains a draft and saved data stays unchanged.
